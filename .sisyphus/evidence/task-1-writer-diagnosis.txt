================================================================================
ROOT CAUSE ANALYSIS
================================================================================

The "No data to write" pattern confirms bluest L2CAP queue backing up:

1. Initial burst of MMP/SMP traffic succeeds (handshake, TreeAnnounce)
2. SessionSenderReport triggers 510-byte writes (session payload)
3. CoreBluetooth bluest queue fills up (bounded(16) without credit monitoring)
4. Subsequent writes block indefinitely
5. Tokio timeout fires after 3 seconds, but bluest never drains
6. TCP window exhaustion cascades - no data can be sent
7. Receiver (Linux side) sends ReceiverReport, but cannot receive new data
8. MPPI metrics show increasing RTT jitter, eventual disconnect

macOS Central (bluest): 3s timeout too short, write queue never drains
macOS Peripheral (objc2): write_maxLength==0 treated as fatal error instead of backpressure

================================================================================
RECOMMENDATION
================================================================================

Implement credit-aware flow control in both writer paths:

1. macOS Central: Read L2CAP TX credits, backpressure when credits == 0
2. macOS Peripheral: Retry write_maxLength==0 with exponential backoff
3. Both: Add credit recovery mechanism (timeout + re-request credits)
4. FIPS layer: Add credit monitoring, throttle send rate on credit exhaustion
