BLE INDEFINITE WEDGE AUDIT
==========================
Date: 2026-04-17
Task: 7 — Verify no BLE path blocks indefinitely without timeout/backpressure outcome

QUESTION: Can any BLE send path block forever?
ANSWER:   NO — all paths have bounded waits with explicit timeouts.


PATH-BY-PATH ANALYSIS
======================

1. Linux BluerStream::send() / send_urgent()
   -------------------------------------------
   Code (io.rs:324-331):
     tokio::time::timeout(BLE_SEND_TIMEOUT, self.conn.send(&framed))
       .await
       .map_err(|_| TransportError::Timeout)

   Analysis:
   - self.conn.send() is a kernel SeqPacket write. It blocks when socket buffer full.
   - Wrapped in timeout(15s). If kernel write doesn't complete in 15s → Timeout.
   - Maximum block time: 15 seconds. BOUNDED.


2. macOS Central BluestStream::send() / send_urgent()
   ----------------------------------------------------
   Code (io_macos.rs:189-204):
     match self.tx.try_send(framed) {
       Ok(()) => Ok(()),
       Err(TrySendError::Full(framed)) => {
         tokio::time::timeout(BLE_CENTRAL_SEND_TIMEOUT, self.tx.send(framed))
           .await
           .map_err(|_| TransportError::Timeout)?
       }
     }

   Analysis:
   - try_send() is non-blocking. Succeeds immediately if queue has space.
   - On Full: timeout(15s, tx.send()). If queue doesn't drain in 15s → Timeout.
   - The drain task (io_macos.rs:1270-1279) reads from channel and writes to bluest.
     If bluest write fails, drain task exits, channel closes → Closed error.
   - Maximum block time: 15 seconds. BOUNDED.


3. macOS Peripheral PeripheralStream::send() / send_urgent()
   -----------------------------------------------------------
   Code (io_macos.rs:699-715):
     loop {
       let notified = self.queue_space_notify.notified();
       if self.output_delegate.try_enqueue(framed) {
         self.notify_write();
         return Ok(());
       }
       match tokio::time::timeout(BLE_PERIPHERAL_SEND_TIMEOUT, notified).await {
         Ok(()) => continue,    // space freed, retry enqueue
         Err(_) => return Err(TransportError::Timeout),
       }
     }

   Analysis:
   - try_enqueue() is non-blocking (checks VecDeque count + byte cap).
   - On full: waits for Notify signal with 15s timeout.
   - Notify fires when drain_to_stream() dequeues data and calls notify_waiters().
   - If drain doesn't free space in 15s → Timeout.
   - Maximum block time: 15 seconds per retry. Total worst case: 15s. BOUNDED.


4. MockBleStream::send() (TEST ONLY)
   -----------------------------------
   Code (io.rs:1131-1135):
     self.tx.send(data.to_vec())
       .await
       .map_err(|_| TransportError::SendFailed("channel closed".into()))

   Analysis:
   - mpsc::channel(64) bounded. send().await blocks when full.
   - NO timeout. However:
     - This is test-only code (cfg(test))
     - Test pairs always have a consumer reading from the paired receiver
     - Tests are expected to consume data; infinite blocking in a test = test bug
   - NOT a production concern.


EDGE CASES CHECKED
===================

Q: Can drain_to_stream() in peripheral path block forever?
A: No. It's called synchronously from the NSStreamDelegate callback on the
   runloop. write_maxLength returns immediately (non-blocking per Apple docs).
   res < 0 = error → return. res == 0 = backpressure → return + retain data.
   res > 0 = partial write → loop continues until done or blocked.

Q: Can the central drain task block forever?
A: No. write_all() on bluest's piper-based writer is async. If the underlying
   NSOutputStream stalls, piper backpressures. The drain task awaits write_all()
   which resolves when data is written or the channel errors. Error → task exits,
   channel closes → next send returns Closed error.

Q: Can Linux SeqPacket send block forever?
A: No. 15s timeout wraps it. Also, kernel socket timeouts exist but we don't
   rely on them — our tokio::time::timeout is the primary guard.

Q: What about recv() paths?
A: recv() in all paths is used with recv_timeout_secs (45s) from config in
   mod.rs receive_loop. That's a separate audit scope but also bounded.


CONCLUSION
============

ALL production BLE send paths have bounded wait times with 15s timeouts.
No path can block indefinitely. The wedge risk identified in Tasks 1-2
(has been fully addressed in Tasks 5-6 for macOS, and was already fixed
for Linux in a prior session).

VERIFIED: No indefinite wedge possible in BLE send paths.
